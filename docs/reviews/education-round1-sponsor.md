## Evidence that matters to sponsor fit

- `README.md`, “NVIDIA Nemotron on Nebius Token Factory,” establishes runtime model roles and honestly excludes Serverless Jobs. CPU verification is not a sponsor weakness by itself: the model's role is interpretation and proposals, while independent tools decide outcomes.
- `src/countertrace/learning.py:18–35` selects observations from the fixed library, includes candidate RTL and an authored facilitator focus, validates cited edges, and explicitly makes feedback advisory. Edge validity does not check whether an explanation is true, useful, or appropriately restrained.
- `docs/evidence/learning-coach-2026-10-05.json` preserves all three development attempts. The first two followed a mistaken read-pointer hypothesis; the final Ultra response redirects attention to the full-write guard. Since both prompt and model changed, this is evidence of one working development configuration, not an Ultra-versus-Super result or a coaching success rate.
- `apps/web/src/views/LearnView.tsx:99–105` discloses source/provenance, authored hints, local live coaching, and the recorded coaching example. The example explicitly says it is not a response to the learner's text and preserves the earlier failures in linked evidence. This is a strong honesty choice.
- `docs/submission/DEMO_SCRIPT.md` gives the sponsor a meaningful role at 1:00–1:25 and actual independently checked repair at 2:10–2:35. The proposed passing-simple-test → revealing-boundary-test sequence makes the learning concept understandable. Keep the recorded/live labels in frame and allow enough time to read the coaching hint and rejected candidate.

## Prioritized fixes within current scope

1. **P1 — Rewrite the actual Devpost fields and testing path around the delivered education product.** `docs/submission/DEVPOST.md:23–80` still leads with the older coding agent and five workbench steps; its model table omits coaching. `docs/submission/TESTING.md` starts with the showcase repair instead of the lab. Replace the main pitch and feature sequence with predict → investigate → explain → transfer; follow with the engineering workbench as supporting evidence. Include all four model roles and explicitly distinguish hosted authored hints from local model coaching. Keep future arbitrary uploads and new module families as deferred possibilities, not the immediate educational roadmap. Acceptance: a judge following only the submitted fields reaches the same experience shown in the script.
2. **P1 — Run a small frozen coaching check across all three lessons before expanding claims.** Use several authored reflections per lesson: a mistaken cause, correct reasoning, vague reasoning, and an overclaim after passing evidence. Hold model and prompt fixed, preserve every response, and rate factual accuracy, responsiveness, answer leakage, and unsupported claims against written criteria. Keep this development evaluation separate from learner evidence. `learning.py:23` already supplies the diagnosis, so test whether the response adapts usefully to the explanation rather than simply repeating that focus. A human educator review would strengthen it; coding can prepare the protocol now.
3. **P2 — Make live coaching evidence inspectable in practice records.** `LearnView.tsx:65–73` keeps returned hint text only in transient state; `apps/web/src/lib/learning.ts` exports counts but no coaching transcript. Preserve request sequence/reflection, response, model identity, and success/error status locally in the optional export. Count attempted and delivered assistance separately. This lets a facilitator interpret assistance and investigate misleading feedback without turning the model into a grader.
4. **P2 — Add an explicit education-to-repair handoff after the learning activity.** The home currently links to a generic runs page. A short, direct link to the existing rejected-then-accepted repair example would demonstrate why the same evidence discipline matters for real Nemotron proposals. Label that the learner candidates are authored and the workbench candidate is a recorded model proposal. No new repair functionality or model family is needed.

## External limitations and release dependencies

- Real learner and instructor participation is needed to assess usefulness. Automated tests, a polished script, and additional assistant panels cannot substitute for it. A small observed pilot can report task completion, misconceptions, assistance, and transfer responses without claiming general learning gains.
- Project-funded live judge access still needs an operational route and funding. `docs/submission/TESTING.md` already acknowledges this; supplying one's own paid API key is a developer setup path. The [official testing provision](https://nebiusglobalaihackathon.devpost.com/rules) requires free access through judging. This review does not declare that recorded replay alone is disqualifying; it identifies an unresolved access dependency for the advertised live capabilities.
- The owner must record, publish, and submit the video and replace draft placeholders. No score above assumes footage already exists. Availability through the judging period and final eligibility are not established by this review.
